Workflow Foundations

01 — A Reproducible Analytics Pipeline

A typical analytics process moves through four stages: Collect → Store → Analyze → Share

Collect: APIs, web, sensors
Store: Drive, files, DBs
Analyze: Python, SQL, AI
Share: Notebooks, reports
Reproducibility: Another analyst should be able to inspect what data you used, what code you executed, and how you arrived at your conclusions.

Data Infrastructure

03 — Data Storage Landscape

  • Drive: simple personal/student working files.
  • Data Lake & Warehouse: raw big data and curated analytical reporting at enterprise scale.
  • Database: managed queryable data for applications and transactions.
  • GitHub: code, notebooks, documentation, and versioned history.
Choose storage based on the job: IA 340 starts with simple cloud file storage, then transitions to relational and NoSQL databases later.
Course Architecture

04 — Why We Use Google Drive in IA340

For Week 2, Google Drive is our working-data layer because it is simple, persistent, browser-based, and seamlessly connects to Colab.

  • Good fit: personal, student, and small-team files such as diamonds.csv.
  • Not an enterprise data lake: enterprise lakes require scalable object storage, security, and governance policies.
IA340 approach: start simple now; move toward enterprise storage and relational databases in subsequent modules.
Interactive Compute

05 — Google Colab: Python in Your Browser

Google Colab is a browser-based Jupyter/Python environment: write Python, run code online, and view results interactively.

  • Zero Local Setup: no Python/Jupyter installation needed; common data science libraries are built-in.
  • Cloud Runtime: runs in any browser on personal laptops, Macs, and lab workstations.
Runtime ≠ Persistent Storage: Colab runtimes are temporary and reset when idle. Keep data in Drive and explicitly save finished work to GitHub.

Version Control

11 — A Repository Is Files + Project History

A standard folder only holds current files. A GitHub repository tracks files plus the complete history of how the project evolved:

  • Commits: What changed, when, and why?
  • Branches: Where can changes be prepared and tested safely?
  • Pull Requests: What change is being proposed for review?
  • Main Branch: The accepted, authoritative project state.
