SQL practice

HAVING: filter the groups

SELECT fips, COUNT(*) AS years_available, AVG(population) AS mean_population
FROM public.population
WHERE year BETWEEN 2015 AND 2024 AND fips LIKE '51%'
GROUP BY fips
HAVING AVG(population) > 200000
ORDER BY mean_population DESC, fips;

WHERE picks input rows. GROUP BY fips forms one group per area. HAVING keeps areas whose mean stored population is above 200,000.

Try 300,000 instead. It changes the result, not the stored data.

SQL practice

JOIN syntax: which table, which column?

SELECT name.name, population.year, population.population
FROM public.population
INNER JOIN public.name
  ON population.fips = name.fips
WHERE population.year = 2024;

Both tables have a column named fips, so in a JOIN we often write table.column to show exactly which field we mean.

SQL Read it as
name.name column name from table name
population.year column year from table population
population.population column population from table population
population.fips = name.fips match the observation's foreign key to the county's primary key

SELECT chooses the output columns. FROM gives the first table. JOIN adds the second table. ON says how the rows match.

Later, aliases make the same SQL shorter: population AS p means p.fips is short for population.fips.

SQL practice

RIGHT JOIN: the same result after swapping tables

SELECT n.fips, n.name, p.population
FROM public.population AS p
RIGHT JOIN public.name AS n
  ON p.fips = n.fips AND p.year = 2024
WHERE n.fips LIKE '51%'
ORDER BY n.fips;

Yes: this example returns the same result as the earlier LEFT JOIN.

name LEFT JOIN population keeps every name. After swapping the table positions, population RIGHT JOIN name still keeps every name.

The result has 133 names: 30 with a 2024 population, and 103 with a missing population. LEFT and RIGHT describe the table positions in the query.

SQL practice

FULL JOIN: keep both sides, using only two tables

SELECT n.fips, n.name, p.year, p.population
FROM public.name AS n
FULL JOIN public.population AS p
  ON n.fips = p.fips
ORDER BY n.fips, p.year;

A FULL JOIN keeps unmatched rows from either table. A blank population means there was no matching observation.

In our extract, every population row has a name parent. The result has 270 matched observations + 103 names without observations = 373 rows. It therefore matches this same all-years LEFT JOIN; a different join type need not change the result on this dataset.

Join measurements using FIPS and year

SELECT n.fips, n.name, p.year, p.population, i.income
FROM public.name AS n
JOIN public.population AS p ON n.fips = p.fips
JOIN public.income AS i ON p.fips = i.fips AND p.year = i.year
WHERE n.fips LIKE '51%' AND p.year BETWEEN 2015 AND 2024
ORDER BY n.fips, p.year;

The full query returns 270 rows, one area-year per row; the screenshot shows the beginning of the result. Matching only FIPS would pair different years and produce 2,430 rows, not 270.

SQL practice

Nested query: compute a value, then use it

Interactive demonstration: Nested MAX step by step | Open demonstration separately ↗

The inner query finds a maximum. The outer query finds every row equal to it, including any exact ties.

SQL practice

Nested query: run one MAX example

SELECT fips, year, income
FROM public.income
WHERE year = 2024
  AND income = (
      SELECT MAX(income)
      FROM public.income
      WHERE year = 2024
  )
ORDER BY fips;

The inner SELECT finds 177,567. The outer SELECT returns the row(s) with that value: 51107 / 2024 / 177567 in this export. The name table identifies 51107 as Loudoun County. Keep tied maxima rather than choosing an arbitrary row.

SQL practice

Self-join: one table, two aliases

Interactive demonstration: Pair consecutive years from the same table | Open demonstration separately ↗

prev means the starting row; curr means the ending row. We are reading the same table twice, not creating another table.

SQL practice

Self-join: only the population table

SELECT curr.fips, curr.year,
       prev.population AS previous_value,
       curr.population AS current_value,
       100.0 * (curr.population - prev.population)
             / prev.population AS growth_rate_pct
FROM public.population AS curr
JOIN public.population AS prev
  ON curr.fips = prev.fips
 AND curr.year = prev.year + 1
WHERE curr.fips LIKE '51%'
  AND prev.year >= 2015 AND curr.year <= 2024
  AND prev.population > 0 AND curr.population >= 0
ORDER BY curr.fips, curr.year;

One table, two aliases: prev supplies year − 1; curr supplies year. 100.0 × (current − previous) / previous gives a percentage, not a fraction.

The query returns 210 rows: seven valid one-year intervals for each of 30 areas. This class example reads all covered areas. It returns only years with an available previous year. Your own question can retain missing rates as NULL, as in the later Fairfax result.

SQL practice

What is a VIEW?

A view is a saved query that you can read like a table.

We have just joined name, population, and income. Instead of rewriting that JOIN every time, we give its SELECT definition the name county_year.

Interactive demonstration: A saved JOIN queried like a table | Open demonstration separately ↗

An ordinary view stores the query definition, not an extra copy of the population/income rows. Querying it uses the underlying data visible at that time. It simplifies SQL; it is not automatically a speed boost.

PostgreSQL views

SQL practice

Save the JOIN as a view

CREATE OR REPLACE VIEW public.county_year AS
SELECT n.fips, n.name, p.year, p.population, i.income
FROM public.name AS n
JOIN public.population AS p ON n.fips = p.fips
JOIN public.income AS i ON p.fips = i.fips AND p.year = i.year
WHERE n.fips LIKE '51%' AND p.year BETWEEN 2015 AND 2024;

A normal view saves this SELECT definition, not another copy of its result rows. Replace only this teaching view, not an unrelated object.

Indexes can help suitable searches, but take storage and maintenance work. An index does not change the query's intended answer.

SQL practice

An existing index on FIPS

The required primary key on name.fips already has an index. An index can help a selective lookup avoid scanning every row.

A table can have more than one index, but indexes use space and must be maintained during INSERT/DELETE and relevant UPDATE operations. Do not index every column. This lesson does not create or remove indexes.

SQL practice

What makes a good data question?

A good question for this lab has three features

1. Specific — name the county/city, years, measure, and comparison.

Example: “For Fairfax County, what was the population change from 2023 to 2024?”

2. Answerable with our data — use fields and years that actually exist in name, population, and income.

Bad example: “What happened in 2025?” We do not have 2025 data.

3. Repeatable — another person using the same county, years, data, and calculation should get the same result.

And remember: correlation does not imply causation. A relationship in these tables does not prove that one variable caused another.
